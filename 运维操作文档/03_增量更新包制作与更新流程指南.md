# 增量更新包制作与更新流程指南

## 一、更新类型自动判定规则

### 1.1 增量更新 vs 全量更新
系统根据文件变更类型自动判定更新类型：

| 变更内容 | 更新类型 | 说明 |
|----------|----------|------|
| 仅配置文件（config/、version.config） | **增量更新** | 仅打包变更文件 |
| 核心代码（source/core/*.py） | **全量更新** | 打包全部核心文件 |
| 无旧版本manifest | **全量更新** | 首次更新或基准丢失 |

### 1.2 文件分类
- **core类型**：`source/core/*.py`、`*.exe`、启动脚本
- **config类型**：`config/*`、`version.config`
- **resource类型**：`resources/*`
- **doc类型**：`*.md`、`*.txt`

## 二、更新包体积优化原理

### 2.1 增量压缩效果
纯配置变更场景下，增量更新包体积可缩减**70%以上**：
- 仅打包变更文件
- 依赖manifest哈希对比精确识别变更
- ZIP压缩进一步减小体积

### 2.2 体积对比示例
| 更新类型 | 文件数 | 包体积 | 缩减比例 |
|----------|--------|--------|----------|
| 全量更新 | 14 | 4.9 KB | - |
| 增量更新（仅配置） | 2 | 1.4 KB | **70.6%** |

## 三、手动生成更新包

### 3.1 通过GUI生成
1. 点击【更新包】按钮
2. 点击【生成更新包】
3. 查看生成结果（类型、大小、缩减比例）

### 3.2 生成的文件位置
```
config/update_packages/
├── update_incremental_4.2.0_1723456789.zip
├── update_full_4.2.0_1723456790.zip
└── update_manifest.json
```

### 3.3 更新包内容
每个更新包包含：
1. 变更文件（按类型打包）
2. `update_manifest.json`（文件哈希列表）

---

## 四、应用更新包

### 4.1 自动更新流程
1. 点击【更新包】按钮
2. 在列表中选择要应用的更新包
3. 点击【应用选中更新】
4. 等待更新完成
5. 重启程序

### 4.2 更新校验流程
系统自动执行以下校验：
1. **manifest完整性校验**：检查文件哈希是否匹配
2. **版本号一致性校验**：验证version.config版本号
3. **失败自动回滚**：任一步骤失败自动恢复备份

### 4.3 更新失败回滚
- 更新前自动创建备份（`config/backup/backup_时间戳/`）
- 校验失败自动恢复备份
- 回滚后程序保持可用状态

## 五、version.config配置规范

### 5.1 版本号规范
```json
{
  "major_version": 4,
  "minor_version": 2,
  "patch_version": 0,
  "version_string": "4.2.0",
  "build_number": 20260709
}
```

### 5.2 更新渠道配置
```json
{
  "release_channel": "stable",  // stable | beta | dev
  "update_url": ""              // 留空使用本地更新
}
```

## 六、分发更新包

### 6.1 分发流程
1. 生成更新包（增量或全量）
2. 将ZIP文件复制到目标机器的`config/update_packages/`目录
3. 目标机器通过GUI应用更新

### 6.2 注意事项
- 增量更新需确保目标机器有对应版本的旧manifest
- 首次更新或版本跨度大时建议使用全量更新
- 更新包不支持跨大版本升级（如4.1→4.2需全量）

---

## 七、常见问题解答

### Q1：为什么生成的是全量更新而不是增量？
**A**：核心代码（source/core/*.py）有变更，系统自动切换为全量更新以确保完整性。

### Q2：更新失败后如何恢复？
**A**：系统自动回滚到备份版本，程序保持可用。检查ERROR日志定位失败原因。

### Q3：如何跳过校验强制更新？
**A**：不建议跳过校验。如有特殊情况，手动解压更新包并替换文件。
